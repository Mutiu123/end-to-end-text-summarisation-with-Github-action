# Project Description — STAR Method

> End-to-End Text Summarisation API with GitHub Actions CI/CD

---

## Situation

I needed to build a production-grade machine learning API that could take raw text input and return concise, abstractive summaries. The project was not just about getting a model to work — it was about demonstrating the full lifecycle of an ML application, from research and experimentation through to automated deployment with enterprise-level security, monitoring, and reliability. The target audience included both end users consuming the API and engineering teams who would maintain, scale, and extend it in production environments. There was no existing infrastructure, no pre-built pipeline, and no deployment automation — everything had to be designed and implemented from scratch on a modern Python stack.

---

## Task

My responsibility was to design, implement, and deploy the entire system end to end. Specifically, I needed to:

- Research and select an appropriate transformer model for abstractive text summarisation, then fine-tune it on a dialogue-specific dataset.
- Build a reproducible, multi-stage ML training pipeline that could be rerun independently at any stage without starting from scratch.
- Wrap the trained model in a production-ready REST API with proper request validation, error handling, and documentation.
- Implement a multi-layered security architecture covering authentication, rate limiting, input sanitisation, and container hardening.
- Integrate async database logging for audit trails and prediction tracking without blocking API response times.
- Set up a full observability stack with Prometheus metrics collection, Grafana dashboards, and structured JSON logging with request correlation.
- Containerise the application using Docker with multi-stage builds and orchestrate production deployment on Kubernetes with auto-scaling, health checks, and network policies.
- Automate the entire lint, test, build, and deploy cycle using GitHub Actions with separate stages and quality gates.
- Write a comprehensive test suite covering unit tests for each layer and integration tests for the full API flow, enforcing a minimum 80% code coverage threshold.

---

## Action

I built this project in a deliberate sequence where each phase fed into the next. Below is a step-by-step account of what I implemented, how I implemented it at the code level, what alternatives I considered at each decision point, and why I chose the approach I did.

---

### Step 1: Project Scaffolding and Configuration Architecture

The first thing I built was the configuration system because every other component depends on it. I created a `Settings` class in `src/textSummarizer/config/settings.py` that inherits from Pydantic's `BaseSettings`. This class defines 30+ typed fields covering application metadata (`APP_NAME`, `APP_VERSION`, `APP_ENV`), security parameters (`SECRET_KEY`, `JWT_ALGORITHM`, `JWT_EXPIRATION_MINUTES`, `RATE_LIMIT_REQUESTS`, `RATE_LIMIT_WINDOW_SECONDS`), database connection details (`MONGODB_URL`, `MONGODB_DB_NAME`, `MONGODB_MIN_POOL_SIZE`, `MONGODB_MAX_POOL_SIZE`, `MONGODB_CONNECT_TIMEOUT_MS`, `MONGODB_SERVER_SELECTION_TIMEOUT_MS`), monitoring flags (`ENABLE_METRICS`, `METRICS_PREFIX`), and model paths (`MODEL_PATH`, `TOKENIZER_PATH`, `MAX_INPUT_LENGTH`, `MAX_SUMMARY_LENGTH`, `NUM_BEAMS`, `LENGTH_PENALTY`).

- I used a regex-based `Field` validator on `APP_ENV` with the pattern `^(development|staging|production)$` to enforce that the environment value is one of exactly three allowed strings. This catches configuration errors at startup rather than at runtime when a request hits a conditional branch that checks the environment.
- I added computed `@property` accessors like `allowed_origins_list` that splits the comma-separated `ALLOWED_ORIGINS` string into a Python list, and `is_production` / `is_development` boolean flags that downstream code can use without repeating string comparisons. I chose computed properties over storing these as separate environment variables because it avoids redundancy and keeps the `.env` file flat.
- I wrapped the `Settings` instantiation in a `get_settings()` function decorated with `@lru_cache()` from `functools`. This creates a singleton -- the environment variables are parsed exactly once on the first call, and every subsequent call returns the cached instance. The alternative I considered was a module-level global variable, but `lru_cache` is more testable because you can call `get_settings.cache_clear()` in test teardown to reset the singleton between tests.
- I configured the `model_config` dictionary inside the Settings class with `env_file=".env"`, `env_file_encoding="utf-8"`, and `case_sensitive=True`. I chose Pydantic BaseSettings over alternatives like `python-dotenv` with manual `os.getenv()` calls because BaseSettings gives me type coercion (strings from `.env` are automatically cast to `int`, `float`, `bool`), validation (invalid values raise immediately), and documentation (the class itself serves as a schema of all required configuration). I considered `dynaconf` as an alternative, which supports multiple file formats and environments natively, but decided against it because Pydantic BaseSettings integrates directly with FastAPI's dependency injection system without any adapter code.
- For the ML pipeline, I created a separate YAML-based configuration in `config/config.yaml` rather than using environment variables. I did this because ML pipeline configuration is hierarchical (each stage has its own `root_dir`, `source_URL`, file paths) and YAML represents nested structures more naturally than flat environment variables. I considered TOML (which is now standard in Python via `pyproject.toml`), but YAML is the established convention in the ML community and is what HuggingFace tooling expects.
- I created a `template.py` script that programmatically generates the full project directory structure, including all `__init__.py` files. I considered using `cookiecutter` which is the standard Python project templating tool, but a custom script gave me exact control over the structure without requiring users to install an additional tool or maintain a template repository.
- I split dependencies into `requirements.txt` (60 production packages) and `requirements-test.txt` (pytest, httpx, coverage tools). I considered using `pyproject.toml` with optional dependency groups (`[project.optional-dependencies] test = [...]`), which is the modern Python standard, but kept separate files because the Dockerfile `COPY requirements.txt .` pattern is simpler and more widely understood in CI/CD pipelines.
- I set up `pre-commit` hooks via `.pre-commit-config.yaml` with Black (formatting), isort (import sorting), flake8 (PEP 8 linting), mypy (type checking), trailing whitespace removal, end-of-file fixing, YAML syntax validation, and large file blocking (500KB threshold). I configured Black and isort with a 100-character line length and set isort to use the `black` profile so their formatting rules do not conflict. I considered `ruff` as a single replacement for flake8 and isort (it is significantly faster and combines both tools), but chose the traditional toolchain because it is more widely adopted and each tool can be updated independently.

### Step 2: ML Research and Experimentation

Before writing any production code, I worked through the entire ML workflow in Jupyter notebooks under `research/`. I created five notebooks, one for each pipeline stage, plus an exploratory notebook for end-to-end prototyping.

- I evaluated four transformer architectures for the summarisation task. BART (Bidirectional and Auto-Regressive Transformer) was my first candidate because it performs well on CNN/DailyMail benchmarks, but its pre-training objective (denoising corrupted text) is general-purpose and not specifically tuned for summarisation. T5 (Text-to-Text Transfer Transformer) was my second candidate because it frames every NLP task as text-to-text, which provides flexibility, but that generality means it does not have a structural advantage for summarisation specifically. GPT-2 was my third candidate because it generates fluent text, but it is auto-regressive only (left-to-right), meaning it cannot attend to the full input when generating, which limits its ability to capture document-level meaning. I selected PEGASUS (Pre-training with Extracted Gap-sentences for Abstractive Summarisation) because its pre-training objective -- masking entire sentences that are identified as important using ROUGE scoring and then predicting them -- directly mimics the summarisation task. This means the model is already optimised for the exact capability I need before fine-tuning even begins. Specifically, I used the `google/pegasus-cnn_dailymail` checkpoint as the starting point.
- I chose the SAMSum dataset (Sampled and Matched Summarisation) for fine-tuning because my target use case is summarising conversational text, and SAMSum contains 14,732 training examples, 818 validation examples, and 819 test examples of human-written dialogue paired with human-written summaries. I considered the CNN/DailyMail dataset (which is larger at 300k+ examples), but it consists of news articles rather than dialogues, and the domain mismatch would have hurt quality on conversational inputs. I also considered the XSum dataset (BBC articles with single-sentence summaries), but its single-sentence constraint is too restrictive for dialogue summarisation where the summary often needs multiple sentences to capture the key information.
- In the training notebook (`04_model_trainer.ipynb`), I experimented with hyperparameters and settled on: `num_train_epochs=1` (sufficient for demonstration and transfer learning from a strong checkpoint), `per_device_train_batch_size=1` (constrained by GPU memory since PEGASUS has 568 million parameters), `gradient_accumulation_steps=16` (effectively simulating a batch size of 16 without requiring the memory for it), `weight_decay=0.01` (standard L2 regularisation to prevent overfitting on the relatively small SAMSum dataset), `learning_rate=2e-5` (conservative rate that works well with pre-trained transformers), and `warmup_steps=500` (gradual learning rate increase to avoid destabilising the pre-trained weights). I considered using the `Trainer` class from HuggingFace versus writing a custom PyTorch training loop. I chose `Trainer` because it handles mixed precision, gradient accumulation, checkpoint saving, and evaluation automatically, and the custom loop would have added 200+ lines of boilerplate without any benefit for my use case.
- For evaluation, I computed ROUGE-1 (unigram overlap), ROUGE-2 (bigram overlap), ROUGE-L (longest common subsequence), and BLEU (n-gram precision with brevity penalty) scores. I chose this combination because ROUGE measures recall (how much of the reference summary is captured) while BLEU measures precision (how much of the generated summary is relevant), and using both gives a balanced view. I considered using BERTScore (semantic similarity via contextual embeddings), which correlates better with human judgments, but it requires a separate BERT model loaded in memory during evaluation and the computational cost was not justified for this project's scope.
- I stored all pipeline artifacts under a structured `artifacts/` directory where each stage writes to its own subdirectory: `artifacts/data_ingestion/`, `artifacts/data_validation/`, `artifacts/data_transformation/`, `artifacts/model_trainer/`. I chose this flat directory structure over a version-tagged approach (like MLflow's artifact store or DVC's cache) because it is simpler to inspect and does not require additional tooling. I considered integrating MLflow for experiment tracking and artifact versioning, but decided against it because it introduces a tracking server dependency and the project currently runs single experiments rather than hyperparameter sweeps.

### Step 3: ML Training Pipeline (Production Code)

I converted the notebook experiments into a modular production pipeline with clear separation between configuration, components, and orchestration.

- I designed a two-layer architecture for each pipeline stage: a **component** class in `src/textSummarizer/conponents/` that contains the actual logic (download, validate, tokenise, train, evaluate), and a **pipeline stage** class in `src/textSummarizer/pipeline/` that reads the configuration and instantiates the component. I chose this separation because it lets me test components independently with mock configurations, and it lets me replace the configuration source (YAML, database, API) without touching the component logic. I considered a single-class approach where each stage reads its own config, but that couples configuration parsing to business logic and makes unit testing harder.
- The `ConfigurationManager` class in `src/textSummarizer/config/configuration.py` reads both `config/config.yaml` and `params.yaml` at construction time and provides typed getter methods (`get_data_ingestion_config()`, `get_model_trainer_config()`, etc.) that return dataclass instances. I chose dataclasses over plain dictionaries because they provide attribute access, type hints, and IDE autocomplete. I considered Pydantic models (consistent with the API layer), but the ML pipeline does not need the validation and serialisation features that Pydantic provides, and dataclasses have zero runtime overhead.
- The `main.py` entry point runs all five stages sequentially with try/except blocks around each stage so that a failure in any stage reports which stage failed and the specific error. I considered using a workflow orchestrator like Airflow, Prefect, or Luigi to manage stage dependencies and retries. I decided against it because the pipeline is linear (no branching or parallelism), runs infrequently (only when retraining), and adding an orchestrator would require a scheduler service, a metadata database, and a web UI -- infrastructure that provides no value for a five-step sequential pipeline.
- Data ingestion downloads a ZIP archive from a GitHub URL using `urllib.request.urlretrieve()` and extracts it with Python's `zipfile` module. I considered using the HuggingFace `datasets.load_dataset("samsum")` API which handles downloading and caching automatically, but I wanted the pipeline to work with arbitrary datasets that might not be in the HuggingFace Hub. The URL-based approach is more general and the download source is configurable via `config.yaml`.
- Data transformation uses the PEGASUS tokenizer (`AutoTokenizer.from_pretrained("google/pegasus-cnn_dailymail")`) to convert raw text into token IDs. I tokenise both the dialogue (input) and summary (target) with `max_input_length=1024` and `max_target_length=128` tokens. I chose these limits based on PEGASUS's architecture (maximum 1024 input tokens) and the observation from my research notebooks that 95% of SAMSum summaries fit within 128 tokens. I used HuggingFace's `Dataset.map()` with `batched=True` for tokenisation because it processes examples in batches and is significantly faster than iterating one example at a time.

### Step 4: FastAPI Application Architecture

I built the API layer using a factory pattern with lifespan management, dependency injection, and a strict middleware pipeline.

- I implemented the `create_app()` factory function in `app.py` that constructs and returns a fully configured `FastAPI` instance. The factory reads `Settings`, configures CORS, adds the request tracking middleware, registers global exception handlers via `register_exception_handlers(app)`, and mounts the Prometheus metrics endpoint at `/metrics` using `prometheus_client.make_asgi_app()`. I chose the factory pattern over direct module-level configuration because it makes the app testable -- test code can call `create_app()` to get an isolated instance without shared global state. I considered using FastAPI's `APIRouter` with sub-applications for better modularity, but the API has only six routes and splitting them across routers would add indirection without improving clarity.
- I used FastAPI's `@asynccontextmanager` lifespan handler (the `lifespan` function) to manage startup and shutdown. On startup, it calls `setup_structured_logging()` to configure JSON log formatting, initialises Prometheus metrics with `get_metrics()`, connects to MongoDB with `await db.connect(settings)`, and loads the PEGASUS model with `_load_model(settings)`. On shutdown, it calls `await db.close()`. I chose the lifespan context manager over the older `@app.on_event("startup")` / `@app.on_event("shutdown")` decorators because the context manager pattern (introduced in FastAPI 0.95+) guarantees that shutdown code runs even if startup raises an exception, and the old event decorators are officially deprecated. I considered lazy model loading (load on first request) instead of eager loading at startup, but that would cause the first request to have unpredictable latency (several seconds to load a 568M parameter model) and would complicate health checks -- the `/health` endpoint would not know whether the model is healthy or simply has not been loaded yet.
- The model loading function `_load_model()` uses a global variable `_prediction_pipeline` rather than attaching the model to `app.state`. I chose a global because FastAPI's `Depends()` system cannot inject `app.state` attributes cleanly -- you would need a custom dependency that accepts the `Request` object and reads `request.app.state.model`. The global is simpler and equally testable (you can mock it in tests). I set a Prometheus gauge `model_loaded` to 1 on success or 0 on failure so that monitoring dashboards show model availability in real time.
- I defined strict Pydantic v2 request schemas in `src/textSummarizer/schemas/requests.py`. The `PredictRequest` model enforces `text` as a required string with `min_length=10` and `max_length=10000`, `max_length` (output tokens) with `ge=10` and `le=512` defaulting to 128, `num_beams` with `ge=1` and `le=16` defaulting to 8, and `length_penalty` with `ge=0.1` and `le=2.0` defaulting to 0.8. I added a `@field_validator("text")` that rejects strings containing only whitespace even if they meet the minimum length. I chose Pydantic v2 over v1 because v2 is rewritten in Rust (via `pydantic-core`) and is 5-17x faster at validation, which matters when every request goes through schema validation. I considered using marshmallow (the other popular Python validation library), but it does not integrate with FastAPI's automatic OpenAPI documentation generation -- Pydantic models are automatically reflected in the Swagger UI.
- I defined response schemas in `src/textSummarizer/schemas/responses.py` with five models: `PredictResponse` (summary, input/output lengths, processing time in milliseconds, request ID, model name), `StatusResponse` (status, version, environment, model loaded flag), `HealthResponse` (overall status, API health, database health as a dictionary, model status), `TokenResponse` (access token, token type, expiry in seconds), and `ErrorResponse` (error boolean, status code, message, optional request ID, optional detail dictionary). I chose to define explicit response models rather than returning plain dictionaries because response models provide automatic serialisation, documentation, and type safety -- if I accidentally omit a field, Pydantic raises an error rather than silently returning incomplete data.
- I built a custom exception hierarchy in `src/textSummarizer/exceptions.py` with a base `AppException` class and five specific subclasses: `ModelNotFoundError` (503), `ModelInferenceError` (500), `InputValidationError` (422), `DatabaseConnectionError` (503), `AuthenticationError` (401), and `RateLimitError` (429). Each exception carries a `message`, `status_code`, and `detail` dictionary. I registered four global exception handlers via the `register_exception_handlers()` function: one for `AppException` (custom errors), one for `HTTPException` (FastAPI/Starlette errors), one for `RequestValidationError` (Pydantic validation failures, where I transform the raw Pydantic errors into a structured list of field/message/type objects), and one catch-all for unhandled `Exception` (returns a generic 500 without leaking stack traces). Every error response includes the `request_id` from `request.state` so that error reports can be correlated with logs. I considered using FastAPI's built-in exception handling without customisation, but the default Pydantic validation error format is deeply nested and not friendly for API consumers -- my custom handler flattens it into a readable list.
- I chose Uvicorn as the ASGI server with 2 worker processes for production. I considered Gunicorn with Uvicorn workers (`gunicorn -k uvicorn.workers.UvicornWorker`), which provides better process management (automatic worker restarts on crashes), but the Dockerfile health check and Kubernetes liveness probes already handle crash recovery, making Gunicorn's process management redundant. I set 2 workers (not more) because each worker loads a full copy of the PEGASUS model into memory (approximately 2GB), so more workers would multiply memory usage without proportional throughput gains since inference is CPU-bound, not I/O-bound.
- The prediction endpoint (`POST /predict`) follows a strict processing order: rate limit check, input sanitisation, model availability check, inference with `time.perf_counter()` timing, Prometheus metric recording (input length histogram, prediction duration histogram, output length histogram, success/error counter), structured audit logging via the `AuditLogger`, and finally async MongoDB logging via `db.log_prediction()`. I chose `time.perf_counter()` over `time.time()` for latency measurement because `perf_counter()` uses the highest-resolution monotonic clock available on the OS, is not affected by system clock adjustments, and has nanosecond precision on modern systems. `time.time()` can jump backwards if NTP adjusts the system clock.

### Step 5: Security Layer Implementation

I implemented security as a layered pipeline where each layer is independent and can reject a request without relying on any other layer.

- I implemented JWT authentication in `src/textSummarizer/security/auth.py` using the `PyJWT` library. The `create_access_token()` function takes a data dictionary and the Settings object, copies the data, adds `exp` (expiry timestamp calculated as current `time.time()` plus `JWT_EXPIRATION_MINUTES * 60`) and `iat` (issued-at timestamp), then encodes everything using `jwt.encode(payload, settings.SECRET_KEY, algorithm=settings.JWT_ALGORITHM)`. The `verify_token()` function calls `jwt.decode()` with the same key and algorithm, and catches two specific exceptions: `jwt.ExpiredSignatureError` (returns 401 with "Token has expired") and `jwt.InvalidTokenError` (returns 401 with "Invalid token"). I added `headers={"WWW-Authenticate": "Bearer"}` to both error responses because RFC 6750 requires this header when rejecting Bearer token authentication. I chose HS256 (HMAC with SHA-256, symmetric) over RS256 (RSA with SHA-256, asymmetric) because there is only one service both creating and verifying tokens -- symmetric signing is faster and does not require managing a public/private key pair. If I had multiple services that need to verify tokens independently, I would switch to RS256 so that only the auth service holds the private key and other services verify with the public key. I considered using `python-jose` instead of `PyJWT` as it supports additional algorithms (including JWE encryption), but `PyJWT` is lighter, has fewer dependencies, and I do not need token encryption since the JWT payload contains only a username and timestamps, not sensitive data.
- I implemented the `get_current_user()` function as a FastAPI async dependency that takes `credentials: Optional[HTTPAuthorizationCredentials] = Depends(security_scheme)` and `settings: Settings = Depends(get_settings)`. I used `HTTPBearer(auto_error=False)` for the security scheme, which means FastAPI does not automatically reject requests without a Bearer token -- instead, `credentials` is `None` and my code explicitly raises a 401 with a descriptive message. I chose `auto_error=False` over `auto_error=True` (the default) because the default error message is generic ("Not authenticated") and does not include the request ID. By handling the None case myself, I can provide a more informative error message and maintain consistent error formatting across all endpoints.
- I built the `TokenBucketRateLimiter` class in `src/textSummarizer/security/rate_limiter.py` from scratch. The class initialises with `max_tokens` (default 100 from settings) and `window_seconds` (default 60), and computes a `refill_rate` of `max_tokens / window_seconds`. It stores per-client state in a `defaultdict` where the key is the client IP and the value is a tuple of `(current_tokens: float, last_check_time: float)`. On each request, the `check()` method extracts the client IP (checking `X-Forwarded-For` first for proxied requests, falling back to `request.client.host`), calculates how many tokens to add based on elapsed time since the last check (`elapsed * refill_rate`), caps at `max_tokens`, and if the bucket has at least 1 token, decrements and allows the request. If the bucket is empty, it raises an `HTTPException` with status 429 and a `Retry-After` header set to `window_seconds`. I used `time.monotonic()` instead of `time.time()` for the timer because `monotonic()` is guaranteed to never go backwards (immune to NTP adjustments), which prevents a scenario where a clock adjustment could artificially refill all buckets. I considered three alternative algorithms: (1) Fixed window counting, which is simpler but allows twice the rate at window boundaries (a client could send 100 requests at 59 seconds and 100 more at 61 seconds). (2) Sliding window log, which is perfectly accurate but requires storing a timestamp for every request, using O(n) memory per client per window. (3) Redis-based distributed rate limiting using `redis-cell` or a Lua script, which would support horizontal scaling across multiple pods, but adds a Redis dependency and network round-trip on every request. I chose token bucket because it handles bursts gracefully (a client that was idle accumulates tokens and can burst up to 100 requests), uses O(1) memory per client (just two floats), and the in-memory approach is sufficient since Kubernetes distributes traffic across pods roughly evenly via the Service load balancer.
- I built input sanitisation in `src/textSummarizer/security/sanitizer.py` with three functions. First, `sanitize_text()` strips whitespace, removes null bytes (`\x00`), strips control characters (byte range `\x01-\x08`, `\x0b`, `\x0c`, `\x0e-\x1f`, `\x7f`) while preserving newlines and tabs, escapes HTML entities using `html.escape(text, quote=True)`, and truncates to `max_length`. Second, `validate_text_length()` checks minimum (10) and maximum (10,000) character bounds and returns an error string or None. Third, `contains_suspicious_patterns()` checks the lowercased text against eight regex patterns: `<script[\s>]` (script tag injection), `javascript:` (URI-based XSS), `on\w+\s*=` (inline event handler injection like `onerror=`), `\{\{.*\}\}` (template injection for Jinja2/Angular), `\$\{.*\}` (expression language injection), `__import__` (Python code injection), `eval\s*\(` (JavaScript/Python eval injection), and `exec\s*\(` (Python exec injection). I chose pattern-based detection over a full WAF (Web Application Firewall) like ModSecurity because the patterns are specific to my input domain -- the text field is for natural language summarisation, so there is no legitimate reason for any of these patterns to appear. I considered using the `bleach` library for HTML sanitisation, but `bleach` is designed for allowing safe HTML tags (like `<b>` and `<i>`) while stripping dangerous ones, and I do not want any HTML tags in my input at all -- `html.escape()` is the correct tool for complete HTML entity escaping.
- I configured CORS middleware in the `create_app()` function using FastAPI's `CORSMiddleware` with `allow_origins` loaded from `settings.allowed_origins_list` (parsed from the comma-separated `ALLOWED_ORIGINS` environment variable), `allow_credentials=True`, `allow_methods=["GET", "POST"]` (restricting to only the HTTP methods the API uses), and `allow_headers=["*"]`. I chose to restrict methods to GET and POST rather than using the permissive `["*"]` because the API does not have PUT, PATCH, or DELETE endpoints, and limiting methods reduces the surface area for unexpected requests. I considered using a reverse proxy (NGINX) for CORS handling instead of application-level middleware, but application-level CORS is simpler to configure, does not require an additional service in the Docker Compose stack, and the settings are visible in the same codebase rather than split across infrastructure configuration.
- For container-level security, I created a non-root user in the Dockerfile with `groupadd -r appuser && useradd -r -g appuser -d /app -s /sbin/nologin appuser`, set the working directory ownership with `COPY --chown=appuser:appuser . /app`, and switched to that user with `USER appuser` before the `CMD`. The `-r` flag creates a system user (no home directory in `/home/`, no login shell), and `-s /sbin/nologin` prevents interactive shell access even if an attacker gains container access. I considered using a distroless base image (Google's `gcr.io/distroless/python3`) which has no shell, no package manager, and no utilities at all, providing even smaller attack surface. I chose against it because distroless images make debugging extremely difficult -- you cannot `docker exec` into the container and run `curl` to test endpoints or `ls` to check file permissions. The non-root user approach gives me most of the security benefit while retaining debuggability.
- I implemented Kubernetes NetworkPolicy resources that restrict ingress traffic to the application pods, allowing connections only from pods with specific labels matching the Ingress controller and the Prometheus scraper. All other pod-to-pod communication is denied by default. I considered using a service mesh (Istio or Linkerd) for network security, which provides mTLS between services and more granular traffic policies, but a service mesh adds significant operational complexity (sidecar proxies, control plane, certificate management) and is over-engineering for a single-service deployment.
- I stored all secrets (JWT signing key, MongoDB connection string, AWS credentials) in Kubernetes Secret resources (base64-encoded) and in Docker environment variables passed at runtime via `-e` flags. I created a `.env.example` file that documents every required variable with placeholder values so that developers know what to configure without seeing actual secrets. I considered using HashiCorp Vault or AWS Secrets Manager for dynamic secret rotation, but the added infrastructure complexity is not justified for this project's scale -- Kubernetes Secrets with proper RBAC are sufficient.

### Step 6: Database Integration

- I chose MongoDB as the database for audit logging. The alternative was PostgreSQL, which I use regularly and is my default choice for structured data. However, the prediction audit records are JSON-shaped documents with fields that may evolve over time (adding new metrics, removing deprecated fields), and MongoDB's schema-flexible document model accommodates these changes without migrations. I also considered SQLite for simplicity (no server process, file-based), but SQLite does not support async I/O and does not have connection pooling, both of which are critical for a FastAPI application that uses `async/await` throughout.
- I implemented the `MongoDBManager` class in `src/textSummarizer/database/mongodb.py` as a singleton using `__new__()`. The `__new__` method checks if `_instance` is None, and if so, calls `super().__new__(cls)` to create the single instance. All subsequent calls return the same instance. I chose `__new__()` over the `@lru_cache()` approach I used for Settings because the MongoDBManager has mutable state (the `_client` and `_database` attributes change when `connect()` and `close()` are called), and `lru_cache` semantics are designed for pure functions. The `__new__` singleton is more appropriate for stateful objects. I considered a dependency injection container (like `dependency-injector` library) for managing singletons, but that adds a framework dependency for what is a straightforward pattern.
- The `connect()` method creates an `AsyncIOMotorClient` with configurable pool sizes (`minPoolSize` from `MONGODB_MIN_POOL_SIZE`, `maxPoolSize` from `MONGODB_MAX_POOL_SIZE`) and timeouts (`connectTimeoutMS`, `serverSelectionTimeoutMS`). I chose Motor (the async MongoDB driver built on top of PyMongo) over PyMongo's synchronous driver because using a synchronous driver inside an `async def` route handler would block the asyncio event loop, preventing other requests from being processed during the database call. I also considered `beanie` (an async ODM for MongoDB that provides document models similar to Django's ORM), but ODMs add abstraction overhead and the audit logging is simple enough (a single `insert_one()` call) that a raw driver call is clearer and faster.
- After creating the client, I verify connectivity by running `await self._client.admin.command("ping")`. This is important because Motor uses lazy connection -- the `AsyncIOMotorClient` constructor does not actually connect to the database. Without the explicit ping, the application would start successfully even if MongoDB is unreachable, and the first request would fail with a confusing connection error. The ping during startup surfaces configuration problems immediately.
- The `log_prediction()` method inserts a document with `request_id`, truncated `input_text` (first 500 characters to limit storage), full `output_summary`, `input_length`, `output_length`, `duration_ms`, `user_id`, and `created_at` (UTC datetime). I truncate the input text because storing full 10,000-character inputs would quickly consume database storage for what is primarily an audit trail. If the full input is needed for debugging, it can be reconstructed from application logs. The entire method is wrapped in a try/except that logs warnings on failure but does not raise -- this is the fire-and-forget pattern. I chose this over a background task queue (like Celery or `asyncio.create_task()` with error handling) because the `await collection.insert_one()` is already non-blocking (it returns as soon as the write is acknowledged by the MongoDB server), and a task queue would add complexity without reducing latency.
- The `health_check()` method runs the `ping` command with `time.perf_counter()` timing and returns a dictionary with `status` ("connected", "disconnected", or "error") and `latency_ms`. This is consumed by the `/health` endpoint, which aggregates API health, database health, and model health into a single response. I chose to include latency in the health check because a database that is technically reachable but responding in 500ms+ indicates a problem that a simple "connected" status would not reveal. Kubernetes readiness probes use this endpoint, so a degraded database connection can cause pods to be removed from the Service load balancer until the database recovers.
- I added a graceful `is_connected` property that returns `True` only when `_client` is not None. The prediction endpoint checks this property before attempting to log -- if the database is disconnected (for example, if MongoDB was not available at startup), the prediction still succeeds, it just does not write an audit record. This design ensures that a database outage degrades the system (no audit logging) rather than breaking it (no predictions).
- I configured connection pooling with `minPoolSize=10` and `maxPoolSize=50`. The minimum of 10 keeps connections warm and avoids connection establishment latency on the first requests after idle periods. The maximum of 50 prevents the application from overwhelming the database under high load. I chose these defaults based on the expected traffic pattern: the API serves 2-10 pods, each running 2 Uvicorn workers, and the database operation per request is a single `insert_one` that completes in under 5ms. With 20 concurrent workers and sub-5ms operations, 50 connections provide ample headroom.
- I used Docker Compose to run MongoDB alongside the application with a persistent volume mount (`mongodb-data:/data/db`) and a health check (`mongosh --eval "db.adminCommand('ping')"`). The `depends_on` with `condition: service_healthy` ensures the application container does not start until MongoDB is accepting connections, preventing startup race conditions.

### Step 7: Monitoring and Observability

- I defined all Prometheus metrics in a single `AppMetrics` class in `src/textSummarizer/monitoring/metrics.py`, instantiated as a singleton via the `get_metrics()` function. The class creates 13 metrics across five categories. For requests: `requests_total` (Counter with labels for method, endpoint, status_code), `requests_in_progress` (Gauge with method and endpoint labels), and `request_duration_seconds` (Histogram with custom buckets at 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s, 5s, 10s). For predictions: `predictions_total` (Counter with status label), `prediction_duration_seconds` (Histogram with buckets at 100ms, 500ms, 1s, 2.5s, 5s, 10s, 30s, 60s), `prediction_input_length` (Histogram with character count buckets at 50, 100, 250, 500, 1000, 2500, 5000, 10000), and `prediction_output_length` (Histogram with buckets at 10, 25, 50, 100, 250, 500). For authentication: `auth_attempts_total` (Counter with result label). For rate limiting: `rate_limit_hits_total` (Counter). For the database: `db_operations_total` (Counter with operation and status labels) and `db_operation_duration_seconds` (Summary with operation label). For system status: `model_loaded` (Gauge, 1 or 0) and `app_info` (Info metric with version and environment). I chose Histogram over Summary for latency metrics because Histograms allow server-side percentile calculation in PromQL using `histogram_quantile()`, and they can be aggregated across multiple pod instances. Summaries calculate percentiles on the client side and cannot be aggregated, which makes them unsuitable for multi-replica deployments. I used Summary only for database operation duration because database operations happen less frequently and the pre-calculated quantiles are convenient for quick checks. I chose custom histogram buckets tailored to expected latency ranges rather than the Prometheus default buckets (which go up to 10 seconds in large steps) because the default buckets are too coarse for an API where P95 latency should be under 1 second.
- I built the `RequestTrackingMiddleware` class in `src/textSummarizer/monitoring/middleware.py` by extending Starlette's `BaseHTTPMiddleware`. The `dispatch()` method first checks for an `X-Request-ID` header (allowing clients to pass their own correlation ID) and falls back to generating a `uuid.uuid4()` if none is provided. It stores this ID on `request.state.request_id` so downstream route handlers can access it. It increments the `requests_in_progress` gauge, records `time.perf_counter()`, calls `await call_next(request)`, records the duration, decrements the gauge, increments the `requests_total` counter with the status code, observes the duration on the `request_duration_seconds` histogram, and adds `X-Request-ID` and `X-Process-Time` response headers. I wrap the `call_next()` in a try/except so that even if the route handler raises an unhandled exception, the middleware still decrements the in-progress gauge and records a 500 status metric -- without this, a crash would leave the gauge permanently incremented. I considered using FastAPI's built-in middleware hooks (`@app.middleware("http")`) instead of a class-based middleware, but the class-based approach is more structured and allows storing state (like the metrics instance) as instance attributes.
- I implemented structured JSON logging in `src/textSummarizer/monitoring/structured_logging.py` with a custom `JSONFormatter` class that extends `logging.Formatter`. The `format()` method constructs a dictionary with `timestamp` (UTC ISO 8601 via `datetime.now(timezone.utc).isoformat()`), `level`, `logger` name, `message`, `module`, `function`, `line` number, `service` name, and `environment`. It conditionally adds `request_id`, `user_id`, and `extra_data` if those attributes exist on the log record. If the record has exception info, it serialises the exception type, message, and full traceback into a nested `exception` dictionary. The final output is `json.dumps()` with `default=str` as a fallback serialiser for any non-standard types (like `datetime` objects that are not JSON-serialisable by default). I chose JSON logging over the default Python log format (timestamp + level + message as a flat string) because JSON is machine-parseable -- log aggregation tools like ELK Stack, Datadog, or CloudWatch Logs Insights can index and query individual fields. I considered using `structlog` (a third-party structured logging library that is popular in the Python community), which provides processors, binding, and a cleaner API. I chose the standard library approach because it avoids an additional dependency and integrates naturally with FastAPI's and Uvicorn's existing logging infrastructure without requiring adapter configuration.
- I created an `AuditLogger` class that wraps the standard Python logger with domain-specific methods: `log_prediction()` records prediction events with request ID, input/output lengths, duration, and status; `log_auth_event()` records authentication events with event type, success flag, client IP, and optional failure reason (logging successful events at INFO level and failures at WARNING level); and `log_rate_limit()` records rate limit violations with client IP and endpoint. I chose to implement audit logging as a separate logger class rather than mixing audit events with application logs because audit events have a specific structure and may need to be routed to a separate log stream in production (for example, security audit logs might need to be sent to a SIEM system while application debug logs stay in CloudWatch).
- I set up the `setup_structured_logging()` function that clears all existing handlers from the root logger, attaches a new `StreamHandler` pointed at `sys.stdout` with the `JSONFormatter`, and suppresses verbose Uvicorn access and error logs by setting their log level to WARNING. I redirect to stdout (not stderr) because container orchestrators like Docker and Kubernetes capture stdout as the standard log stream, and many log collectors expect structured logs on stdout. I suppress Uvicorn's built-in access logs because my `RequestTrackingMiddleware` already logs every request with more detail (including the correlation ID), and having both would produce duplicate entries.
- I set up the Prometheus scrape configuration in `monitoring/prometheus.yml` with a single scrape job targeting the app container at port 8080 on the `/metrics` path with a 15-second scrape interval. I chose 15 seconds over the default 60 seconds because ML inference latency can spike quickly under load and a 60-second interval would miss short-lived incidents. I considered 5-second intervals for higher resolution, but that increases Prometheus storage consumption and CPU usage proportionally, and 15 seconds is sufficient for the alerting thresholds I would set (typically requiring sustained anomalies over minutes, not seconds).
- I pre-built a Grafana dashboard as a JSON file in `monitoring/grafana/dashboards/text-summarizer.json` with panels for request rate, latency percentiles, error rates, model inference duration, and database health. I set up auto-provisioning via `monitoring/grafana/dashboards/dashboard.yml` (which tells Grafana to load dashboards from the file system on startup) and `monitoring/grafana/datasources/prometheus.yml` (which registers Prometheus as the default datasource). I chose file-based provisioning over manual dashboard creation through the Grafana UI because provisioned dashboards are version-controlled, reproducible, and automatically available in every environment. I considered using Grafana Cloud (managed service) instead of self-hosted Grafana, but self-hosted keeps the monitoring stack self-contained within the Docker Compose / Kubernetes deployment and avoids a paid external dependency.

### Step 8: Containerisation and Orchestration

- I wrote a multi-stage Dockerfile with two stages. Stage 1 (`builder`) uses `python:3.10-slim-bookworm` as the base, copies only `requirements.txt`, and runs `pip install --no-cache-dir --prefix=/install -r requirements.txt`. The `--prefix=/install` flag installs all packages into a separate directory tree rather than the system Python. Stage 2 (`production`) starts from a fresh `python:3.10-slim-bookworm` base, installs only `curl` (needed for health check), creates the non-root user, copies the installed packages from the builder stage with `COPY --from=builder /install /usr/local`, and copies the application code. I chose multi-stage over single-stage because the builder stage contains pip, setuptools, wheel, and potentially C compilation tools (gcc, build-essential) that are needed to compile packages like `numpy` or `torch` extensions, but none of these are needed at runtime. Excluding them from the production image reduces the image size by hundreds of megabytes and eliminates tools that an attacker could exploit. I considered using `python:3.10-alpine` instead of `slim-bookworm` for an even smaller image, but Alpine uses `musl` libc instead of `glibc`, and many Python packages (especially PyTorch and scientific computing libraries) are compiled against `glibc` and either fail to install or require long compilation times on Alpine.
- I configured the Docker health check with `HEALTHCHECK --interval=30s --timeout=10s --start-period=60s --retries=3 CMD curl -f http://localhost:8080/health || exit 1`. The `--start-period=60s` is critical because the PEGASUS model takes significant time to load into memory, and without a start period, Docker would mark the container as unhealthy and restart it before the model finishes loading, creating a restart loop. I chose 60 seconds based on observed model loading times. The `--retries=3` means Docker waits for three consecutive failures before marking the container unhealthy, preventing transient network hiccups from triggering restarts.
- I set production environment defaults directly in the Dockerfile with `ENV APP_ENV=production LOG_LEVEL=INFO HOST=0.0.0.0 PORT=8080`. These can be overridden at runtime with `docker run -e` flags or Docker Compose environment configuration, but having sensible defaults means the container works correctly even if no environment variables are passed. I chose to set defaults in the Dockerfile rather than relying solely on the Pydantic Settings defaults because the Dockerfile makes the production configuration explicit and visible in the infrastructure definition.
- I designed the Kubernetes deployment in `k8s/deployment.yaml` with 3 replicas and a rolling update strategy with `maxSurge: 1` and `maxUnavailable: 0`. This means Kubernetes creates one new pod, waits for it to pass readiness checks, then terminates one old pod, repeating until all pods are updated. The `maxUnavailable: 0` ensures zero downtime -- at no point during the update are there fewer than 3 healthy pods serving traffic. I configured liveness probes (`httpGet /health` every 30 seconds, with `failureThreshold: 3`) and readiness probes (`httpGet /health` every 10 seconds, with `initialDelaySeconds: 30`). The readiness probe has a shorter interval because it controls whether the pod receives traffic -- a 10-second interval means a recovered pod is re-added to the load balancer within 10 seconds, while the liveness probe's 30-second interval is acceptable because it only controls pod restart decisions. I considered using startup probes (a Kubernetes feature for slow-starting containers) instead of a large `initialDelaySeconds` on the liveness probe, but startup probes require Kubernetes 1.18+ and `initialDelaySeconds` is more universally compatible.
- I implemented the Horizontal Pod Autoscaler in `k8s/hpa.yaml` with `minReplicas: 2`, `maxReplicas: 10`, and a target CPU utilisation of 70%. I chose 70% rather than the commonly used 80% because ML inference is CPU-intensive and latency degrades non-linearly above 70% CPU -- at 80%, the operating system starts scheduling contention and response times can spike 3-5x. I set `minReplicas: 2` (not 1) because a single replica means any restart or deployment update causes downtime, and the PodDisruptionBudget requires at least 2 available pods. I considered memory-based autoscaling (scaling on memory utilisation) in addition to CPU, but memory usage is stable once the model is loaded -- it does not increase with request volume -- so CPU is the correct signal for scaling decisions. I also considered using KEDA (Kubernetes Event-Driven Autoscaling) with custom Prometheus metrics (like `requests_in_progress`) as the scaling trigger, which would be more responsive than CPU-based scaling, but KEDA requires a separate installation and the CPU-based HPA is built into Kubernetes.
- I created the PodDisruptionBudget with `minAvailable: 2`, ensuring that voluntary disruptions (node drains during cluster upgrades, spot instance reclamation, manual scaling operations) cannot reduce the running pod count below 2. I chose `minAvailable` over `maxUnavailable` because `minAvailable` is an absolute guarantee regardless of the current replica count, while `maxUnavailable` is relative and its behaviour changes as the HPA scales up or down.
- I set up Kustomize with a base `kustomization.yaml` that lists all 11 resources and environment-specific overlays in `overlays-staging.yaml` and `overlays-production.yaml`. The overlays patch replica counts (2 for staging, 3 for production), resource limits (smaller for staging, larger for production), and environment variables (DEBUG=true for staging, DEBUG=false for production). I chose Kustomize over Helm because Kustomize is built into `kubectl` (no separate installation), uses plain YAML patches instead of Go templates, and is simpler for a single-application deployment. Helm's template system and chart repository model is more powerful for distributing reusable packages across teams, but this project is a single application deployed to specific clusters, not a reusable package.
- I created a ServiceMonitor resource for Prometheus Operator integration. In clusters that use the Prometheus Operator (which is common in production Kubernetes setups), the ServiceMonitor tells Prometheus to automatically discover and scrape the application's metrics endpoint based on label selectors, without manually editing the Prometheus configuration. I considered using annotations-based discovery (`prometheus.io/scrape: "true"` on the Service) instead, which is simpler but less flexible -- ServiceMonitors allow specifying the metrics path, scrape interval, and TLS configuration per target.

### Step 9: CI/CD Pipeline

- I designed the GitHub Actions workflow in `.github/workflows/main.yaml` as four sequential jobs with explicit `needs` dependencies: `lint`, `test` (needs lint), `build-and-push` (needs test), and `deploy` (needs build-and-push). Each job runs on its own runner and has its own environment setup. I chose GitHub Actions over Jenkins (self-hosted, requires maintenance, Java-based), CircleCI (separate service, requires account), and GitLab CI (requires GitLab as the Git host). GitHub Actions is native to the repository, free for public repos, and uses YAML configuration that lives alongside the code. I structured the pipeline as four separate jobs rather than four steps in a single job because jobs can run on different runner types (the deploy job uses `self-hosted` while others use `ubuntu-latest`), and failed jobs show clearly in the GitHub Actions UI which stage failed.
- The lint job installs Black, flake8, mypy, pylint, isort, and their type stubs (pydantic, pydantic-settings, types-PyYAML), then runs four checks in sequence: `black --check --line-length 100 src/ app.py` (verifies formatting without modifying files), `isort --check-only --profile black --line-length 100 src/ app.py` (verifies import order), `flake8 src/ app.py --max-line-length 100 --ignore E203,W503` (PEP 8 with exceptions for Black-compatible formatting), and `mypy src/ --ignore-missing-imports` (type checking, configured with `continue-on-error: true` because mypy errors are informational rather than blocking -- some third-party libraries lack type stubs and would cause spurious failures). I chose to run mypy as non-blocking because enforcing strict type checking on all third-party library interactions would require extensive type stub maintenance that provides diminishing returns for this project.
- The test job installs both `requirements.txt` and the test dependencies (pytest, pytest-asyncio, pytest-cov, httpx), then runs `pytest tests/ -v --tb=short --cov=src/textSummarizer --cov-report=term-missing --cov-report=xml:reports/coverage.xml --junitxml=reports/test-results.xml` with `APP_ENV=testing` and `SECRET_KEY=test-secret-key-for-ci` as environment variables. I generate coverage in both terminal format (visible in CI logs) and XML format (uploadable as an artifact for later analysis). The `--tb=short` flag truncates tracebacks to show only the relevant frames, keeping CI logs readable when multiple tests fail. I considered using `tox` as a test runner (which manages virtual environments and can test against multiple Python versions), but the project targets a single Python version (3.10) and tox's environment management adds startup time to the CI pipeline without benefit.
- The build-and-push job is conditional: `if: github.ref == 'refs/heads/main' && github.event_name == 'push'`. This ensures Docker images are only built for commits that land on main, not for feature branch pushes or pull requests. The job authenticates to AWS using `aws-actions/configure-aws-credentials@v4` with access key and secret key from GitHub Secrets, logs into Amazon ECR using `aws-actions/amazon-ecr-login@v2`, builds the Docker image, tags it with both `${{ github.sha }}` (the full 40-character commit hash for immutable traceability) and `latest` (for deployment scripts), and pushes both tags. I chose Amazon ECR over Docker Hub because ECR integrates with AWS IAM for authentication and is co-located with the deployment infrastructure (EC2/EKS), reducing image pull latency. I considered GitHub Container Registry (ghcr.io) which integrates natively with GitHub Actions and avoids AWS credentials, but the production deployment runs on AWS and pulling from ECR is faster within the same region.
- The deploy job runs on a `self-hosted` runner because it needs network access to the production server. It pulls the latest image from ECR, stops the existing container with `docker ps -q --filter "name=texts" | grep -q . && docker stop texts && docker rm -fv texts || true` (the `|| true` ensures the step succeeds even if no container is running), starts a new container with `docker run -d -p 8080:8080 --name=texts --restart=unless-stopped` passing all secrets as environment variables, waits 30 seconds for the model to load, verifies health with `curl -f http://localhost:8080/health`, and cleans up dangling images with `docker system prune -f`. I chose direct Docker deployment on the self-hosted runner over Kubernetes deployment via `kubectl apply` because the current production environment is a single EC2 instance. When scaling to multiple instances, I would switch to `kubectl apply -k k8s/` or Helm upgrade, and the Kubernetes manifests are already prepared for that transition.
- I created a separate `tests.yml` workflow that triggers only on pull requests and runs the lint and test jobs but not the build or deploy jobs. This gives pull request reviewers fast feedback (lint and test results appear as PR checks) without wasting time building Docker images for branches that have not been merged yet. I considered combining both workflows into a single file with conditional job execution, but separate files are clearer -- each file has a single responsibility and the trigger conditions are visible in the filename.
- I configured `paths-ignore` in the main workflow to skip CI runs when only documentation files change (`README.md`, `CONTRIBUTING.md`, `DEPLOYMENT.md`, `PRODUCTION_READY.md`, `docs/**`). This avoids wasting CI compute on documentation-only commits that cannot break the application. I considered using path filters on the test and build jobs individually (only run tests if `src/` changed, only build Docker if `Dockerfile` changed), but this granularity creates risk -- a change to `requirements.txt` should trigger tests even though no source code changed, and tracking all the dependency relationships between paths and jobs is error-prone.
- I set the workflow permissions to `id-token: write` and `contents: read`, following the principle of least privilege. The `id-token: write` permission is required for OIDC-based AWS authentication (if I later switch from static credentials to federated identity), and `contents: read` restricts the workflow from modifying repository contents. I considered leaving permissions at the default (which grants broader access), but explicitly restricting permissions is a security best practice recommended by GitHub's documentation.

### Step 10: Testing Strategy

- I built the test infrastructure in `tests/conftest.py` using pytest fixtures. I created fixtures that provide isolated `Settings` instances with test-specific values (test secret key, testing environment), mock database managers, and `httpx.AsyncClient` instances bound to the FastAPI app. I chose `httpx.AsyncClient` over FastAPI's `TestClient` (which is based on `requests` and wraps async code in a synchronous adapter) because `AsyncClient` executes the async route handlers natively on the event loop, which means any async-specific bugs (like forgetting to `await` a coroutine or deadlocking on a shared asyncio lock) are caught by the tests. With `TestClient`, these bugs would be masked because the synchronous wrapper handles the event loop internally. I considered using `pytest-httpx` (which provides httpx response mocking), but the tests call the actual application code rather than mocking HTTP responses, so it is not applicable.
- I wrote `test_auth.py` to cover the full JWT lifecycle: creating a token with valid credentials and verifying the returned string is a valid JWT; decoding a token and verifying the `sub`, `exp`, and `iat` claims match expectations; passing an expired token (created with a negative expiry) and verifying a 401 response with "Token has expired"; passing a token signed with the wrong secret key and verifying a 401 response with "Invalid token"; passing a malformed string (not a valid JWT at all) and verifying rejection; and calling a protected endpoint with no Authorization header and verifying a 401 with "Authentication credentials were not provided". I tested each failure mode separately rather than combining them into a parameterised test because each failure triggers a different code path (`ExpiredSignatureError` vs `InvalidTokenError` vs None credentials) and the error messages differ.
- I wrote `test_rate_limiter.py` to verify the token bucket algorithm at its boundaries: sending requests within the limit and verifying they all succeed; sending exactly `max_tokens` requests and verifying the next one raises HTTP 429; verifying that the 429 response includes the `Retry-After` header with the correct window value; sleeping for a fraction of the window and verifying that tokens have partially refilled (testing the continuous refill behaviour rather than discrete window resets); sending requests from two different client IPs and verifying their buckets are independent; verifying that the `X-Forwarded-For` header is correctly parsed for proxied requests (taking the first IP in a comma-separated list); and calling `reset()` and verifying that all buckets are cleared.
- I wrote `test_sanitizer.py` with positive and negative cases: verifying that clean English text passes through `sanitize_text()` with HTML entities escaped but content preserved; verifying that `contains_suspicious_patterns()` returns True for `<script>alert(1)</script>`, `javascript:void(0)`, `onerror=alert(1)`, `{{constructor.constructor('return this')()}}`, `${7*7}`, `__import__('os')`, `eval(cmd)`, and `exec(cmd)`; verifying that `contains_suspicious_patterns()` returns False for text that contains words like "evaluate" and "execute" which superficially overlap with the patterns but are legitimate English words (testing for false positives); and verifying that `validate_text_length()` returns error messages for text shorter than 10 characters and longer than 10,000 characters, and returns None for valid lengths.
- I wrote `test_schemas.py` to verify Pydantic validation at the boundary conditions: creating a `PredictRequest` with text exactly 10 characters (minimum) and verifying it passes; creating one with 9 characters and verifying it raises a validation error; creating one with only whitespace and verifying the `@field_validator` rejects it; creating one with `num_beams=0` (below minimum of 1) and verifying rejection; creating one with `length_penalty=3.0` (above maximum of 2.0) and verifying rejection; and creating one with all optional fields omitted and verifying the defaults are applied correctly (`max_length=128`, `num_beams=8`, `length_penalty=0.8`).
- I wrote `test_exceptions.py` to verify the custom exception hierarchy: constructing each exception subclass and verifying it carries the correct status code, message, and detail dictionary; verifying that the `register_exception_handlers()` function correctly intercepts `AppException`, `HTTPException`, `RequestValidationError`, and generic `Exception`; and verifying that all error responses include the `request_id` field from the request state.
- I wrote `test_api.py` for integration testing across the full middleware and route handler stack: calling `GET /health` and verifying the response contains `status`, `api`, `database`, and `model` fields; calling `GET /status` and verifying it returns the correct version and environment; calling `POST /predict` without authentication and verifying a 401 response; completing the full authentication flow (POST to `/auth/token`, extract the token, POST to `/predict` with the Bearer token) and verifying a successful prediction response with all expected fields; and sending invalid JSON to `/predict` and verifying the custom validation error format with field-level error details.
- I configured pytest coverage in the workflow to target `src/textSummarizer` while excluding the research notebooks and ML pipeline stage files. I chose this exclusion because the pipeline stages are tested through end-to-end pipeline runs (running `python main.py`) rather than unit tests, and including them in the coverage calculation would artificially deflate the percentage. The 80% threshold applies only to the code that is feasibly unit-testable: configuration, schemas, security, monitoring, database, and exceptions. I considered a higher threshold (90%), but 90% often forces developers to write meaningless tests (like testing that a getter returns its value) just to hit the number, which reduces the signal-to-noise ratio of the test suite.

## Result

### Technical Outcomes

- Delivered a fully functional text summarisation API that accepts raw text (10 to 10,000 characters) and returns abstractive summaries using a fine-tuned PEGASUS model, with configurable inference parameters (beam search width, length penalty, maximum output length) exposed per request.
- Achieved a complete 5-stage ML training pipeline that runs end to end from raw data download through model evaluation, with each stage independently rerunnable and all artifacts stored in a structured, traceable directory layout under `artifacts/`.
- Implemented seven distinct security layers (network policy, TLS, CORS, JWT authentication, rate limiting, input sanitisation, container hardening) providing defence in depth against the OWASP Top 10 attack categories relevant to a text input API.
- Built a rate limiting system that handles 100 requests per 60 seconds per client IP with O(1) per-request overhead and no external dependencies, using the token bucket algorithm to allow legitimate burst traffic while preventing sustained abuse.
- Established a monitoring stack with 10+ Prometheus metrics, a pre-built Grafana dashboard, and structured JSON logging with correlation IDs, giving operators real-time visibility into request throughput, latency percentiles (P50, P95, P99), error rates, model performance, and database health.
- Created a zero-downtime deployment system using Kubernetes rolling updates with readiness probes, a Horizontal Pod Autoscaler (2 to 10 replicas at 70% CPU target), and a PodDisruptionBudget (minimum 2 pods available), ensuring the service remains responsive during deployments and cluster maintenance.
- Automated the full delivery pipeline through GitHub Actions with four quality gates (lint, test, build, deploy), where code quality issues block the pipeline before tests run, test failures block before Docker images are built, and a post-deployment health check verifies the new version is actually serving traffic.
- Achieved a comprehensive test suite covering authentication, rate limiting, input sanitisation, schema validation, configuration management, exception handling, and full API integration, with an enforced 80% minimum code coverage threshold in CI.

### Architecture and Design Outcomes

- Produced a codebase organised by responsibility (config, security, monitoring, database, schemas, pipeline) where every piece of functionality has a single predictable location, reducing the cognitive load for developers navigating the project for the first time.
- Implemented the singleton pattern for Settings, MongoDBManager, and AppMetrics to ensure that expensive resources (environment parsing, connection pools, metric registries) are initialised once and shared across all requests without per-request overhead.
- Used FastAPI's dependency injection system for settings, authentication, and rate limiting, making each dependency mockable in tests and replaceable without modifying the route handlers.
- Designed the Docker containerisation with multi-stage builds that separate build-time dependencies from runtime dependencies, producing a minimal production image with no compilers, no pip, and no build tools — only the Python runtime, curl for health checks, and the application code running as a non-root user.
- Created a configuration system that loads from three sources (environment variables via Pydantic BaseSettings, YAML files for ML pipeline config, Kubernetes ConfigMaps and Secrets for production) with type-safe validation and sensible defaults, so the application works out of the box in development and is fully configurable in production.
- Built the monitoring integration so that Prometheus, Grafana datasources, and Grafana dashboards are all auto-provisioned from configuration files, meaning a fresh `docker compose up` or Kubernetes deployment gets full observability without any manual setup steps.
- Structured the CI/CD pipeline so that pull requests get fast feedback (lint and test only) while main branch pushes get the full pipeline (lint, test, build, deploy), optimising developer experience without sacrificing deployment automation.
- Documented every architectural decision, tool selection, and workflow in dedicated files (PROJECT_ARCHITECTURE.md, WORKFLOW_DIAGRAMS.md, COMPLETE_BUILD_GUIDE.md) with ASCII diagrams, decision rationale tables, and reading guides for different audiences (new developers, debuggers, DevOps engineers, ML engineers).
